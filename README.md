# Meal Planner 

## О проекте

Полнофункциональная информационная система для автоматизации подбора рецептов и планирования питания: формирует персонализированное меню на период до 31 дня с учётом целевых КБЖУ, диетических ограничений, аллергенов, предпочтений и текущих запасов продуктов, генерирует список покупок с вычетом остатков и предлагает гибридные рекомендации рецептов.

## Проблема и цель

Пользователю, который следит за питанием, приходится вручную сопоставлять десятки параметров: калорийность и БЖУ, диетические ограничения, аллергены, наличие продуктов, разнообразие блюд, предпочтения по кухне. Это занимает время и приводит к ошибкам — лишним покупкам, повторяющимся блюдам, нарушению диеты.

**Цель:** спроектировать систему, которая автоматически подбирает сбалансированное меню и список покупок, снижая когнитивную нагрузку и количество ошибок планирования.

## Контекст и ограничения

- Целевое время генерации меню — до 2 секунд на период до 31 дня.
- Глубинные интервью с пользователями не проводились; требования формулировались на основе анализа предметной области и существующих решений.

## Моя роль

Системный аналитик:

- формализация функциональных и нефункциональных требований;
- проектирование модели данных и схемы БД (19 таблиц, 4NF);
- спецификация REST API и контрактов взаимодействия (`api/index.php`, `api/*.php`);
- определение бизнес-правил, контрольных соотношений и критериев приёмки;
- обоснование выбора алгоритмов и структур данных.

## Функциональные требования (реализованные сценарии)

- **Главная (дашборд):** прогресс-бары КБЖУ за сегодня (превышение выделяется красным), виджеты продуктов, покупок и избранного.
- **Рецепты:** расширенный поиск и фильтрация (категория, калорийность, время, сложность), карточки с изображениями, модальное окно с ингредиентами и инструкцией, добавление в избранное.
- **Моё меню:** выбор периода, настройка количества приёмов пищи, блюд и напитков на каждый приём, генерация меню генетическим алгоритмом, ручная замена блюд через альтернативы, печать меню.
- **Продукты:** учёт остатков, добавление через автодополнение, изменение количества, удаление.
- **Покупки:** автоматическая генерация списка с учётом остатков, группировка по категориям, отметка купленного (добавляется в остатки), печать.
- **Профиль:** антропометрия, цель и уровень активности, диетические ограничения (10 масок), аллергии, исключённые продукты, избранные рецепты, история оценок.

## Ключевые проектные решения и компромиссы

### 1. Генетический алгоритм для формирования меню

**Гипотеза:** генетический алгоритм (ГА) позволит одновременно балансировать несколько разнородных критериев — сбалансированность БЖУ, разнообразие, предпочтения пользователя и ограничение калорийности дня (900–4000 ккал) — без жёсткой оптимизации одного показателя.

**Альтернативы:**
- жадный алгоритм — проще, но не гарантирует сбалансированность по всем критериям сразу;
- линейное программирование — даёт оптимальное решение, но сложнее в настройке при нелинейных предпочтениях и ограничениях.

**Компромисс:** выбран ГА с параметрами «популяция 50, поколений 100, мутация 0.05, кроссинговер 0.8, элита 5». Цена — стохастичность результата и необходимость подбора параметров; выигрыш — гибкая настройка функции приспособленности и объяснимое распределение весов между критериями.

**Модель хромосомы:** хромосома — меню на весь период, гены — идентификаторы блюд и напитков. Функция приспособленности учитывает сбалансированность БЖУ (`Balance`), разнообразие (`Variety`, штраф за повтор > 3 раз), соответствие предпочтениям (`Preference`, бонусы за избранное и кухню) и ограничение калорийности дня (900–4000 ккал). Избранные рецепты имеют в 10 раз больший вес при выборе.

### 2. Расчёт целевых КБЖУ

**Решение:** расчёт по формуле Миффлина-Сан-Жеора с последующей корректировкой на активность и цель.

- **BMR:** мужчины — `10×вес + 6.25×рост − 5×возраст + 5`; женщины — `10×вес + 6.25×рост − 5×возраст − 161`.
- **TDEE** = BMR × коэффициент активности (1.2–1.9).
- **Целевая калорийность:** похудение (×0.85), поддержание (×1.0), набор массы (×1.15).
- **Макронутриенты:** белки 25 %, жиры 30 %, углеводы 45 %.

**Почему:** формула Миффлина-Сан-Жеора точнее устаревшей Харриса-Бенедикта и хорошо документирована; фиксированное распределение макронутриентов упрощает первичную настройку и объяснимо пользователю. 

### 3. Хранение диетических ограничений в битовой маске

**Решение:** 10 диетических масок (вегетарианство, веганство, без глютена, кето, палео и др.) хранятся в виде битовой маски.

**Альтернатива:** отдельная таблица связей «пользователь — ограничение».

**Компромисс:** битовая маска упрощает и ускоряет фильтрацию рецептов, но усложняет добавление новых ограничений (требуется миграция). Для текущего набора из 10 масок компромисс приемлем.

### 4. Схема БД в 4NF

**Решение:** 19 таблиц, нормализация до 4NF.

**Почему:** устранение аномалий вставки, обновления и удаления при хранении рецептов, ингредиентов, оценок и меню. Цена — большее количество JOIN-запросов, но для целевой нагрузки пет-проекта это оправдано.

### 5. Гибридная рекомендательная система

**Решение:** итоговая оценка = `0.6 × content + 0.4 × (collab / 5)`, где контентная часть — совпадение кухни (1.0 / 0.5), коллаборативная — средние оценки пользователей из таблицы `recipe_ratings`.

**Компромисс:** контентная фильтрация работает без истории оценок, коллаборативная — улучшает персонализацию по мере накопления данных. Веса подобраны эмпирически; `[УТОЧНИТЬ: проводилось ли сравнение с другими весами или A/B-тестирование]`.

### 6. Формирование списка покупок

**Решение:** агрегация ингредиентов из меню с учётом порций, вычет текущих остатков (`required = max(0, needed − stock)`), группировка по категориям продуктов.

**Почему:** правило `max(0, ...)` гарантирует неотрицательность списка и исключает повторную покупку уже имеющихся продуктов.

### 7. Контрольные соотношения как мост между требованиями и реализацией

Сформулированы проверяемые ограничения, использованные как критерии приёмки:

- КБЖУ рецепта: отклонение ≤ 5 %;
- калорийность дня: 900–4000 ккал;
- повтор рецепта: ≤ 3 раз за период;
- лимиты блюд и напитков на приём;
- неотрицательность остатков (CHECK в БД).

## Технологический стек

- **Сервер:** PHP 8.1, Apache 2.4.
- **База данных:** MySQL 8.0 (19 таблиц, 4NF).
- **Клиент:** HTML5, CSS3 (Bootstrap 5), JavaScript ES6 (модульный).
- **Архитектура:** клиент-серверная, REST API, SPA.

## Артефакты системного аналитика

- ER-диаграмма на основе `db/schema.sql` 
- BPMN-схема процесса «Планирование меню → список покупок» 
- User story и use case для ключевых сценариев (генерация меню, замена блюда, учёт остатков)
- Фрагмент спецификации REST API (OpenAPI/Swagger) на основе `api/` 
- Матрица трассировки «требование → проектное решение → критерий приёмки» 
- Глоссарий предметной области (КБЖУ, BMR, TDEE, диетическая маска, остатки)

**Пользовательский эффект:** снижение времени на планирование рациона и составление списка покупок; прозрачные правила формирования меню и списка покупок.

## Безопасность и нефункциональные аспекты

- Хеширование паролей через `password_hash()` (bcrypt).
- Подготовленные выражения PDO для защиты от SQL-инъекций.
- Экранирование вывода (`escapeHtml`) для защиты от XSS.
- Разграничение ролей (пользователь / администратор).
- `.htaccess` для запрета доступа к конфигурационным файлам.
